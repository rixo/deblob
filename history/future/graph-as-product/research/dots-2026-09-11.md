# Dots collected 2026-09-11 — grammar, plan diff, viz, test titles

Banked from a thread between rixo, Fable and the partner's auditing agent
(terrain, second external dogfood target — nothing partner-identifying here).
Each dot carries its standing: **verified** (read or ran it), **inferred**

## The dots

**1. The verb grammar — hypothesis, under test.** Tag each step of a driver
handler with one verb from a closed set; the tag alone decides the layer:

| Verb                                       | Layer    |
| ------------------------------------------ | -------- |
| parse, call (one per trigger), print, exit | driver   |
| instantiate, connect                       | assembly |
| decide, sequence, infer, result            | service  |
| know, compute                              | model    |
| translate                                  | adapter  |

Two properties make it actionable where "keep it thin" and "until it grows" are
not: no verb has two homes, no home has a threshold. An agent tags a line and
moves it when the tag disagrees with the file, at any size. `catch` is syntax,
not a verb: tag the body (exit, translate, decide); a catch that swallows has no
verb, and that is the finding. Standing: fits every step of one partner verb and
every module-level definition of our `main.ts`. The partner's six remaining verb
rows are the test; the number to report is verbs the set could not tag.

- ? Is `call` one per trigger in every driver shape (plugin hook, HTTP route),
  or only in CLIs?
- ? Is `result` (build the value that carries the outcome) distinct from
  `compute`, or the same verb seen from the service?
- ? Presentation decisions (color from TTY, verbosity): parse + compute in the
  strict reading, so no service. Holds beyond the one case examined?

If it survives: a placement card, drafted after the six rows and riding
placement-debt step 05. Not before.

**2. Plan as skeleton, plan-vs-actual as graph diff — hypothesis.** A deblob
skeleton is files with suffixes, exports and imports: already a plan with no
body code, and already what the graph serializes to. So the plan language could
be the graph's own text form (one line per node with layer and exports, one per
edge); an agent writes the target skeleton; the guard is a diff of two graphs,
nodes, edges and exports added or missing. The partner's README promising five
use cases where the code shipped two is the drift this would show.

- ? Is a graph diff a review object a human reads faster than prose? Untested;
  the spike's second question.
- ? Authoring ergonomics for agents: unknown. Stub `.ts` files are the
  alternative (checkable by `deblob check` as they stand) at the cost of a tree
  full of empty bodies.

- ? Are titles alone enough, without knowing which exports a spec exercises?

**6. Carbon/silicon communication — rixo's framing, inferred from one
artifact.** Agents express nuance in walls of text; the human's information
processing speed is the bottleneck of everything downstream. The auditing
agent's review unit, one row per verb, before and after, "what becomes sayable",
was legible where prose was not. The tool's job would be: generate the before
pane, let agents author the after pane in the plan language, make the diff the
review object.

**7. The picture is for carbon; the schema is what works on silicon — inferred,
one agent's self-report.** The partner's auditing agent, asked what its verb map
had surfaced that the prose spec had not, answered that the picture did nothing
for it. What worked were two constraints of the row format behind it: _mandatory
slots_ (an "owner after" cell that must hold one concrete call — the prose "uses
the same dependency and formatter" reads complete, the cell refuses it) and a
_closed vocabulary at step grain_ (walking a handler line by line and giving
every step one verb exposed a compute filed under printing when the audit had
classified at function grain). rixo's reading: this is a forcing function, not a
shared language — "where does it fit for it to make sense?" proxies "does it
make sense?" because the second question has no failure mode the agent can
detect on its own, and the first has one it cannot hide: an empty or vague slot.
deblob draws the boxes; this draws what is allowed inside a box. Consequences
for the map: the source is the schema (rows, or the graph's text form), the
picture is one rendering of it for the human, and the same rows could feed a
linter. The card's "certified compression for agents" line still holds, but the
agent consumes the text form, never the drawing.

- ? Grain: the rows fix one step per line. Does that grain hold outside CLI
  handlers?
- ? The "what becomes sayable" cell is free text — the one slot where vagueness
  does not show. Can it be constrained (a test title that must exist)?

**8. Zoom has axes, and the card already had them — rixo, materialized in the
spike.** Not a discovery: the card's `--depth` was one axis; the spike made
three visible.

- _Node grain_: services → concepts (port, use cases, adapters, knowledge) →
  files → exports → module-scope internals → functions → variables → the AST.
- _Link grain_: boxes with counts → items → files → named symbols (which export
  an import actually takes — the terrain note's leak tell, `tallySurface`
  reaching `main`, is a symbol-grain link).
- _Per-layer grain_: collapsing one layer to one item while the others stay open
  (the spike's knowledge item, first collapsed, then listing files). Worth
  making controllable per layer.

Open: what the top-level view is (above services: packages, repos — or the
trigger list, the roadbook's index). Open, rixo's instinct says yes: how far
down is worth rendering, since the smallest view is the AST. Fable's read: the
architecture's vocabulary ends at the export; below it the guarantees stop
(tests through the contract, import-invisibility) and the language server is the
right instrument — so the map drills to a symbol and hands off to code rather
than rendering statements. Hypothesis, not a ruling.

**10. Where adapters go — four tries in one afternoon, rixo ruling each.** (a)
Adapters nested inside the port they implement, as sockets: rejected — an
adapter very often lives in another box than its port, the nominal case, so a
socket that only holds same-box adapters lies by omission. (b) rixo's sketch,
rows inside the box: ports / service beside adapters / model. Built; worked;
then rixo: "maybe we're fighting ELK too much by imposing our own spatiality" —
the row chains and reversed edges existed only to force an order the edges would
not produce. (c) Adapters outside the hexagon, in their own box, the classic
ports-and-adapters picture: a hexagon holds ports, service, knowledge; an
"implemented by" edge runs port → adapter wherever the adapter lives. Two edge
kinds, two directions that agree — imports point consumer → provider (drivers
left), implements points port → adapter (world right) — and the left-to-right
axis becomes the roadbook direction (trigger → use case → port → adapter →
world) without a single ordering constraint handed to the layout engine. Inside
a hexagon only real edges are given (service → ports, service → knowledge) and
ELK stacks them. Observed on both codebases: port-less adapters drift left
toward the driver that alone consumes them; real adapters sit right of their
hexagon. Nested adapter-hexagons need no nesting code under (c): they are boxes
with ports of their own plus an implements edge from the parent's port. rixo on
(c): it misrepresents the packaging boundary — the adapters a service ships are
packaged with it, and a separate box says otherwise. (d) The ruling, as
sketched: one box per service, split down the middle. Left half the hexagon
proper as a vertical stack (ports, service, knowledge); right half the adapters
it ships, connecting leftward to the same ports and knowledge; cross-box arrows
arrive from wherever. The split materializes what is packed together while
keeping inside (left) apart from outside-ish (right). Built as two invisible
one-layer stacks per box, model order, one hidden edge saying "adapters after
hexagon", and the short leftward connectors drawn by hand after layout — ELK
still routes everything between boxes. ELK's own layer constraints (FIRST /
LAST) were tried first for the split and refused: a FIRST node may have no
incoming edge, and the hexagon half has internal ones. Standing: (d) is the
current picture on both codebases; rixo has not read it yet.

Also found on the way: ports are types-only by rule, so every import of a port
is a type import — a "type imports off" default hides exactly the port wiring.
Edges into a port file now always draw.

**11. The map draws only the driven side — inferred, from the partner field
note's later addenda (read 2026-09-11 afternoon).** Hexagonal has two sides. The
file conventions name the driven side explicitly (`*.port.ts`, `*.adapter.ts`)
and the driving side only implicitly: the driving port is the service factory's
return type, the driver is "assembly's second hat". So the scanner draws every
driven port as a box and the whole driving side as one node called `main.ts`.
The `useCases` fact the dump already extracts (keys returned per factory) _is_
the driving port — data the map has and does not render as a side. Driver
entries → driving port is many-to-one: several drivers share a use case, a help
screen has none, a use case may await its driver. Listing a driver's
registrations (commands and flags, one extractor per driver flavor the way
classification has flavors) gives the roadbook's index for free.

Three zoom levels, one place per thing: _topology_ (boxes and edges, derived
from code), _route_ (a driving port and what it reaches: services, driven ports,
the adapters assembly binds; source-selection flags pick the binding, mode flags
pick a branch), _flow_ (inside one use-case function: decide, sequence, call,
result; its terminal states are the route's leaves, which are the sayable test
titles). Call order inside a use-case function is AST-extractable as a
heuristic; the verb on each step is not. The correction that matters: the
roadbook is not a permanent third document. In a converged system a CLI verb and
a web action call the same service function and the driver only translates
arguments, so the route view needs no authored input — select a driving port,
highlight what it reaches. Authored rows exist only while drivers hold logic
that should be a driving port; they are the migration ledger of that drift and
should shrink to zero. What stays authored is the spec's API section, where
driving ports are named before they exist. Drivers may be hexagons with their
own ports; ours already is (`MainIo`).

Mess as a graph property, candidates cheapest first, all inferred from one
codebase: _fan-out per trigger_ (services one handler wires; above one is a
laundered verb — the partner's biggest verb touched five); _route length_ (hops
from trigger to effect with no decision on the way: a pipeline in a service
suit); _repeated wiring_ (composition units assembly builds together at two or
more sites are a unit never isolated — frequent edge-set mining on
assembly-origin edges, no new extraction). Standing rule from the same note:
slots as gates, metrics as review prompts that point the reviewer at a row,
never a score to beat — agents satisfy the graded thing, and a single file has
no arrows. Fan-out per trigger is the first metric worth drawing, and it needs
the roadbook edge (dot 13).

**12. The pictures are UML, the product is not — Fable's reading, rixo agreeing
2026-09-11.** Every zoom level has a UML diagram type: topology is the component
/ composite structure diagram (components, ports, provided and required
interfaces; the split box is a composite structure with parts and assembly
connectors; the orange dotted "implements" is the realization arrow); route is
the use case diagram (actor, use case, many-to-one) plus a communication diagram
for the participants; the catalog is Cockburn's textual use case (main scenario,
extensions as variants, briefs by goal level); flow is the activity diagram; the
layer suffix is a stereotype. `Port` is a literal UML 2 construct and hexagonal
borrowed the word; the author of ports-and-adapters is the author of the use
case text book, so topology and roadbook were designed as a pair. Verified: UML
2 ports, Cockburn's authorship. Inferred: the level-to-diagram mapping.

Why UML lost, and how each cause is avoided by construction rather than
discipline: _authored, so it drifted_ (one source here, the picture is a
projection; C4 / Structurizr are the modern attempt and still mostly authored);
_too big_ (three views and the axes of dot 8); _class grain_ (dot 8 stops the
map at the export and hands off to the language server — the anti-UML choice);
_nothing enforced_ (a stereotype is a label; a suffix is a label with CI-checked
properties, which is the whole difference between a diagram and a certified
map). The genuinely novel claim is the closure across levels: topology derived
and certified, driving side derived from the driver flavor, test titles attached
by convention, roadbook shrinking to zero authored rows, only the spec's API
section authored, ahead of the code. UML, C4 and BDD each cover one level, each
authored. Standing: hypothesis, one afternoon behind it. The step-grain verb
grammar (dot 1) has no ancestor beyond fUML action semantics, which nobody used.

Reuse: the names (port, adapter, provided / required interface, actor, use case,
realization — shipped wording lets readers bring their priors; roadbook and
territory stay internal); the notation (lollipop and socket for the split box,
worth a try); Cockburn's brief as the catalog shape; BDD scenario titles as the
leaves (Serenity-style living documentation is the closest existing artifact,
worth one look); mermaid / PlantUML as render targets, never as the model — dot
2's plan language shaped so it can render to mermaid, not written in it. Not
reused: the metamodel and XMI, design-first workflow, class grain, round-trip,
C4's four level names (C4 fixes four different kinds of thing; ours is one role
set at every depth, and that difference is the point).

_Ruling (rixo, 2026-09-11): one meaning per arrow, and UML's meanings — import
is a dashed dependency, implements is a realization, the roadbook edge is a
solid message arrow._

**13. Use cases are the hinge — rixo's hunch; lineage and vocabulary gap
verified 2026-09-11.** The hunch is not original, which is its strength.
Jacobson made "use-case driven" the first adjective of the Unified Process: the
use case model is the one the other models are checked against. Cockburn wrote
both halves. Martin drew use cases as the second ring of Clean Architecture and
named "screaming architecture": a codebase should scream its use cases, not its
framework — the terrain finding is a screaming-architecture failure in the
strict sense, the partner's code screamed pipeline stages. The sdd's GOAL-first
is the same instinct one level up.

The gap, verified: the concept is in deblob's prose and absent from its
vocabulary. architecture.md says each function on the returned API is a use case
and that a service with unnameable use cases is a utility bag; its drivers
section says a driver is a goal. Below the prose nothing carries it: no node
type in the graph, no rule, no extractor, no card word beyond passing mentions
in six knowledge files; the driver is "assembly's second hat" and our own CLI is
six hand-rolled cases in a switch. The one mechanical hook is the flavor's
factory rule — the spike already reads the returned keys and calls them use
cases; they have no edges because nothing points at them. Two definitions wear
the one word (rixo's objection, same evening): deblob's is structural and
level-blind, every function on a returned API; Cockburn's has levels, user goal
/ subfunction / summary, and the partner's stages are subfunctions exposed as
user goals with every rule green. Resolution, inferred from two codebases: the
level is read from the caller — reached from the driving side, a user goal;
reached only from services, a subfunction; both, both — and the driver call
counts only when the trigger reaches exactly one box outside the driver's own (a
driver may be a hexagon with its own services; those calls are translation).
Fan-out is that rule seen from the trigger, which is why it bites the
assembly-eats-logic problem: a driver sequencing three domain services is fixed
by a facade service that owns the sequence, where it gets a contract and a test.
Undecidable by structure: a service-only use case that is a user goal whose
driver does not exist yet. Rule text in step 02's spec; standing measured there.
_Correction 2026-09-12 (rixo)_: the "owner / reached" vocabulary this dot and
step 02 built on was never validated and never landed; withdrawn. The tendency
is "primary use case", a use case called by a trigger, definition still open —
see [driver-extraction-2026-09-12.md](./driver-extraction-2026-09-12.md) §
Decision material. The partner's agent noted the same from outside: cataloguing
use cases and variants is easy for an agent, and deblob offers no affordance to
pull on.

Order of the three dots rixo wants connected (map, steps, use cases): use cases
first, then route, then flow. The map has use cases as items and no driving
side; adding the trigger → use case edge makes "which verb has no owner" a graph
property. Steps live inside one use case and their terminal states are its test
titles, so a flow view with no use-case node has nowhere to hang; flow also
needs the verb grammar (agent declarations, non-deterministic by rixo's ruling)
and the partner's agent said the picture does nothing for it — authored rows
first, drawing second, so it waits. The catalog rixo pictures as a file tree is
Cockburn's brief: one entry per use case, main scenario, variants as extensions;
derived when the driver is thin, authored only in the spec's API section ahead
of the code; a tree cannot hold triggers as parents (many-to-one), so triggers
hang on a use case as attributes. If spike 2 floats, two things graduate through
a spec, never through spike code: use case as a node type in the graph model,
driver as a flavor with one extractor per driver kind. The `create*` check stays
rixo's call.
