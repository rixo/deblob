## Entered canon

- **Two layers outside the hexagon, inward → outward: assembly, then driver.**
  Neither is a composition unit, neither is an adapter. Cockburn's driving
  adapter is the driver with its hooks; Seemann's composition root is assembly.
  Keeping them in separate files with one right each is ours.
- **Assembly** (`.assembly.ts`): the composer. Imports composition units, other
  assemblies, model (factories for a shared dependency-free instance, values as
  arguments, never functions for results — rixo asked why model at all, 09-15),
  blob; never a driver, never tech (tech values arrive as parameters; a
  container library only by explicit config). Every call is a factory call;
  arguments are literals, tech values, instances; returns instances; no use-case
  call, no branch on an instance's output, nothing at module root but imports.
  Imported only by drivers and assemblies, **type imports included** (no
  contract → `runtime-import` does not reach it; consumers type against service
  APIs). Fractal: shared built at the root, flows down by argument or context,
  never sideways. Assembly files are the code-splitting seams. Tone: not an
  evil; the most boring file in the program.
- **Driver** (`.driver.ts` for plain-TS techs; tech files by glob — spec files,
  framework entry points; the shebang hand-off counts as driver): the tech file.
  Wiring outside hooks (assembly calls, tech setup, sub-driver registration;
  args = tech values, instances, literals; wiring may also sit inside a hook,
  lazily). A hook is the callback the tech fires; it may wire and makes exactly
  one use-case call — zero is a violation too. Calls services (use cases,
  getters), assembly factories, sub-driver wiring functions, its own tech; never
  adapters, never models. Defines only hooks and at most one wiring function
  taking the tech. Imports another driver only to call its wiring function with
  tech and instances. **Nothing outside the driver layer imports a driver, types
  included.** "Prelude" dropped as a rule word: wiring is a verb set, hook is a
  position.
- **Slugs** (rixo: most semantically correct, breaking is fine):
  `service-assembly-only`, `adapter-assembly-only` (as code carries them),
  `assembly-builds-only`, `assembly-driver-only`, `wiring-outside-hooks`,
  `one-call-per-hook`, `driver-calls-services-only`,
  `driver-defines-hooks-only`, `driver-to-driver-wiring`, `driver-not-imported`,
  `test-is-assembly-and-driver`; `blob-quarantine` stays assembly-only (rixo,
  09-15: a driver has no legal use for a blob import — its hooks call services;
  a driver that still needs blob stays suffixless; assembly is where blob
  enters, as an instance behind a port the service already holds); `inward-deps`
  reads `… < assembly < drivers`; matrix gains a row.
- **Tests**: a spec file is assembly and driver in one, by the test tech's
  shape; exempt from the call count and services-only; test edges never label
  use-case level; e2e tests are users. A driver's own test is the smoke test
  through the bin.
- **Use-case levels** unchanged: reached from a hook = user goal on that
  channel; only from services = subfunction; annotation, never a violation.
  House alias for subfunction: "instrumental use case" (rixo, 09-15), next to
  "primary use case" for user goal; "secondary use case" stays avoided.
- **Web, one claim only**: a component matching the declared driver globs
  (`+{page,layout}.svelte`, `*.widget.svelte`, or whatever the tech adapter is
  told) may import an assembly; any other component doing so is a violation.
  Everything else web stays research.
- **Not ruled, by choice**: instance duplication — two drivers calling one
  assembly get two instances; visible as fan-in on the map; annotation later if
  ever, no nanny guard.

## The rules, by verb, not by position (ruled in shape; strength open)

Four verbs a driver file may perform: **resolve the driver tech** (cac chain,
express app, argv), **initialize**, **wire**, **call** a service use case; parse
and present are the trigger's translation. Any position: a prelude may live
inside a handler (the code-split-friendly form, the provider shape). The only
positional fact the check keeps is which trigger a definition belongs to, for
attribution — the tech adapter's job and its risk. Findings: a definition in no
verb (residue); a branch over data (a branch whose arms are factory calls is
wiring); a driver calling an adapter (bypasses the hexagon); two service calls
in one trigger — strength open: exactly one, or n primaries with "same service
twice" as the smell; "one per service" rejected, no literature behind it.

Code leaving a driver has two doors: a service, where the service rules apply on
arrival (ports, no adapter calls, coverage) — a wholesale move is not a hole, it
is the design; or a suffixless blob file, counted and quarantined. The driver
file itself has no room: a declared file with a closed verb list cannot absorb a
line without turning red. What the checker does not read is whether tests
justify behavior — the test gate's job until instrumented.

## Web — the questions, not answers (rixo asked for the essence only)

1. What is the trigger? A route, a form action, a component event handler, a
   `load` function — and are server and client triggers the same kind?
2. Where is the prelude? A layout or context provider initializes and wires; a
   component calls. Two files, one layer, two verbs — or does the provider count
   as a driver at all?
3. What is "present" when the output is a component tree? A CLI presents by
   writing a stream. A template branches and loops over data. Is a template a
   driver's presentation, a model, or a third thing the verb list has no name
   for?
4. Who dispatches? The framework owns routing by file convention. The tech
   adapter must read that convention, and there is no `switch` to attribute
   imports from.
5. Where does reactive state sit? A service call returns once; a UI subscribes.
   Stores that hold a service result and drive re-render are neither prelude nor
   call.

## rixo's web take (written blind, before reading the questions) and the overlap

SvelteKit: `+page` files are the entry points, so they are the triggers. The
driver's verbs on the web: resolve the tech (connecting to Svelte) yes; wiring
"maybe, why not"; init in a `.svelte` file "cheesy" — it would bring a frontend
dependency (the Svelte compiler) into the use-case catalog, which has no use for
it. **Init and wiring are not of the same nature and laws** (ruled as
direction): passing a dep around flies anywhere; creating a second

driver's exclusively; wiring is free (the arch already allows it outside the
driver as fractal assembly); the page gets its service from context, which is
wiring, not init. What is left to the page is calling use cases — it is a
trigger, that is the point — and the use case lives in a `.service.ts` under the
full check. The web's biggest specificity: **the use case returns a reactive
object, a "fat store"** with inputs, events and data streams (hypothesis,
rixo's). One page, one call; the page's handlers act on the store.

Overlap with the five questions: Q1 closed (entry point = trigger, one call,
handlers act on the returned store); Q5 closed by the fat store; Q2 mostly
closed, with the init ≠ wiring split as the new rule; Q4 implicit; Q3 (the
template as presentation, model, or a third thing) untouched.

Opened by the take: where init lives in SvelteKit (a plain `.ts` driver file
readable without the compiler — hooks, a root load, a module the root layout

## The web driver's shape (rixo, late; direction, not ruled)

**"Driver is an adapter" holds. The specificity: an adapter with the init
right.** `.svelte` files never init. The app wants central runtime resolution
(the Angular case, seen from the app side): a registry of getters with lazy
auto-init over dynamic imports — code splitting preserved, init once, aware. The
trigger → use-case link is preserved by the `.context.ts` pattern
(`getHugeDataService()` over `getContext`): the page imports the getter, not the
service; the context file type-imports its service. So the link exists twice —
the runtime edge in the driver's registry (`import()`), the static edge through
the context file — and the map draws page → context → service with zero runtime
imports from the page. One carve-out to rule: a `.context` file may type-import
its `.service` (today only blob treats type-only imports as violations, so this
is a narrow exemption). Angular, settled: same mechanism, different ownership —
the registry is ours, one readable file, services never import or decorate, keys
are ours.

Verified the same night: the extraction already yields a runtime edge (form
`dynamic`) for a literal `import()` and surfaces a non-literal `import(expr)` as
an unresolved diagnostic (`extraction.service.spec.ts`), so the registry's edges
are on the map today and a computed-path registry would be loud, not silent. Not
closed: the registry on the server (a module-level lazy singleton is shared
across SSR requests — per-request in hooks/locals on the server, module-level on
the client: the one place the web driver has two shapes); Q3 (the template) and
the fat store's reactivity primitive remain.

## Where the driver lives in the web app (rixo, last word of the night)

The registry does not say where the driver file is. Init is materialized by a
`setFooContext` call most of the time (not always — a driver may pass around
services it did not create), and that call does not belong in `.context`, which
lacks the global vision. Who has the vision? `+page`. Init and calling use cases
are intimately interleaved. The layers stay pure of any frontend dependency by
giving the page its own driver file: `foo/+page.svelte` imports
`foo/page.driver.ts` to get the use case's reactive API — the fat store — and
connects it to its UI. `layout.driver.ts` says what it is on its own. (ruled as
direction: "feels proper".) Consequence for the open list: on the web the driver
is a suffixed file next to the framework's entry point, which moves the
"declaration vs `.driver` suffix" question — the suffix is what the web wants;
the config declaration stays for CLIs without a framework file to sit next to.

## Correction, last (rixo): no lazy auto-init — context IS the registry

**No lazy auto-init. Capital sin** unless one is a chaosmonger. Init stays in
`.driver`, which does both the creation and the `setContext`. `.context` does no
init at all, ever: it is the `service_id → service` map, the central registry
itself — Svelte's context is the registry, no second one. The
registry-of-lazy-getters idea above is dead; so is the need for `import()` for
splitting, since SvelteKit already splits by route and a page driver that inits
statically bundles the service with its page.

Chains on the map: `.svelte → .driver → .context → (type) .service` for a pull;
`.driver → .service` (runtime) for a creation — the init right. So the map shows
which driver created a service and which ones pulled it.

**Alluring rule: only `.driver` may import `.context`.** `createService` vs
`getServiceFromContext` is a loaded decision and must not be left unmanaged.
`layout.driver.ts` and `page.driver.ts` are the same thing: either may create or
pull. A pull nobody set fails loud at runtime, ordering is the layout tree.
`.context` is a new suffix, driver-side: imports the tech (`getContext` /
`setContext`) and its `.service` type-only — the carve-out to rule.

## Web, day two (2026-09-13, evening) — the `.svelte` file, and what we are after

Every ruling below is to be judged by that goal: does it close a door blob could

**Standing:** the whole section is theory until stressed. The stress test is the

### What a `.svelte` file is (inferred, converging)

Neither model nor service. Model is out by the dependency argument (a compiler
dependency in the use-case catalog); service is out by definition (a component
owns a DOM subtree, not use cases). Not a driver either, and the composition law
is the tell: drivers never import drivers (two roots fused), components import
components all day. Two different compositions, one law cannot cover both. So it
is a third thing, and the literature already names it: the view (Cockburn's UI
outside the hexagon, MVP's passive view, Feathers's Humble Object). No new
suffix: the tech names the file.

Root composition on the web, the thing a driver would be chastised for, is done
by the framework by file convention (`+layout` renders a slot, never imports
`+page`) and appears in no import. Q4 from last night closes this way: the tech
adapter reads the route tree, the import reader reads the view tree, the two
never mix.

### Rights, and the tension that shaped them (rixo's tension, ruled in shape)

The tension: `+page` and `+layout` are the web drivers (settled), with the init
delegated to a `.driver` file for legibility. Every other `.svelte` should have
model rights only, or the composition law breaks. But a deep component cannot be
denied `getContext`, and prop drilling is not a way anyone touts.

Resolution: **context right and init right are two rights, and the import rule
separates them mechanically.** Creating a service needs a `.service` import.
Reading the registry needs a `.context` import. A `.svelte` gets the second and
never the first, so it cannot init whatever it does with context. The worst it
can do is `setContext` with something it was handed, which is re-wiring, ruled
free last night ("passing a dep around flies anywhere"). `getContext` in a deep
component is receiving a dependency, the same act as a CLI command handler being
handed its service.

This amends last night's "only `.driver` may import `.context`": the
create-versus-pull decision that rule wanted managed only exists where creation
is possible, and that is only `.driver`. Amended:

- `.driver` may import `.context` and `.service`. Init right: create or pull.
  Exists only where there is an init; a `+page` that creates nothing has no
  `.driver` and pulls like any component.
- `.svelte` may import `.svelte`, `.model`, `.context`, the tech. Compose, pull,
  call. Never `.service`, `.adapter`, `.port`, never init.
- Nobody else imports `.context`. It carries the frontend runtime, and the
  dependency arrow is one-way: `.driver` never imports `.svelte`, so the
  frontend stack does not invade the rest (ruled).

So a `.svelte` has model rights plus wiring plus call. A component that pulls a
service and renders children that pull their own is N triggers nested in a tree,
the way `main.ts` holds N commands flat. No root is fused because no `.svelte`
holds a root right.

The CLI parallel, corrected: the page is the program, not the command. Each
handler is a trigger with its one call; under the fat store the driver made the
one service call and the handlers act on the returned object, so statically the
page made zero service calls. Store versus N plain functions from the driver is
a service-shape question and leaves the `.svelte` rules unchanged.

**The map turns the fear around (inferred):** prop drilling hides a service pass
inside a `.svelte → .svelte` edge; a context pull is a
`.svelte → .context → (type) .service` chain, visible per consumer. deblob has a
reason to lean context for services, the opposite of touting prop drilling.

**Dark by design:** everything inside a template and inside a handler. How many
pulls a component makes, whether it calls at all, what the template branches
over. Not ruled, not instrumented. The laundering-hole goal says this darkness
is acceptable only if the doors are shut: no `.service`/`.adapter`/`.port`
import, no init. Whether that is enough is exactly what the viewer must show.

### Trigger right ≠ init right — the CLI confounded them (rixo's tension, resolved in shape)

The tension, in rixo's words: clicking a button walks and quacks like a trigger,
so it is driver material. But it fires from `Button.svelte`, which sits in
`FooCard.svelte`. FooCard knows the use case and pulls something from context to
bind it to the button; Button knows nothing and feels like a model. In no world
does FooCard get the init right. But the trigger right, yes?

Yes. We observed on the CLI that init and triggers interleave, and assumed one
nature. That was circumstance: one file, one process, one lifetime, both sit
there. The web puts them in different places by its own mechanics: init at the
root, once; triggers wherever an event fires, many, deep. So the driver layer
(Cockburn's primary-adapter ring) has **two kinds of holder**: the root holds
the init right, exclusive; the trigger holds the call right, not exclusive. On
the CLI they coincide in `main.ts`; on the web they never do. Neither definition
changes ("driver = adapter with the init right", "a trigger calls a use case");
what dies is the assumption that they name the same file.

FooCard is a trigger, Button is a view, and the difference is **observable, not
declared**: FooCard imports `.context`, Button imports only `.svelte` and
`.model` and receives a callback prop. Same suffix, two roles, told apart by the
one thing deblob reads.

Verbs by holder on the web: root does init and wire; trigger does wire, call,
parse, present. Attribution stays the tech adapter's job, its unit being the
component rather than a switch case. The CLI findings carry over in principle
(no primary, two calls, definition in no verb); today only the import findings
fire, the rest need a Svelte-aware reader.

**Where the laundering-hole goal bites:** the import doors keep I/O and services
out of FooCard; they do not keep logic out. A handler that grows some computing
before calling the store is the exact shape assembly took. The hole is narrowed
to "model-shaped logic in a trigger component", the same darkness as "knowledge
under first consumer" on the CLI. Tolerable or not is the viewer's question.

Lean, not rule: a trigger handed its store by prop is invisible to the map; one
that pulls from context is visible. A reason to favor context, not to forbid
props.

### `.driver` for triggers, `.assembly` for init — the split (rixo's proposal, late; my CLI read; NOT ruled)

rixo: we were fast to make `.driver` hold triggers AND init. Driver means
triggers, that is the point. Allowing assembly in there fits a CLI; on the web
the sidekick next to the entry point still makes sense but abuses the word, and
triggers live lower than the page (a full-featured `FooSection`, which might
even want its own little context and its own sidekick). "We are circling around
avoiding `.assembly` by fear of the recent burn." Proposal: sidekick `.assembly`
files, with the understanding that components are drivers. Question put: what
does that mean for a CLI, init only in `.assembly` when the triggers (the cac
commands) live in `.driver`?

**The burn was not the name (verified).** `deblob.config.ts` today says
`assembly: ["src/index.ts", "src/drivers/**"]`: assembly was declared, and the
declaration IS the confounding, the whole drivers directory in one bag. What it
lacked was a verb list; the port litmus classified every driver line as assembly
and nothing could reject a trigger, an init or a detector table from that bag. A
suffixed `.assembly` with a closed verb list is the opposite of the hole.

**On deblob's CLI, file by file (`main.ts` today: 435 lines, imports six
adapters, two services, six check models, parses argv, loads config, runs the
detector table, renders):**

- `cli.assembly.ts`: init and wire only. Creates the fs/loader adapters, awaits
  the config load through the config service (the fs kernel), creates engine,
  flavor adapter, extraction, check service. Returns the use cases by value (a
  CLI has no context to set). Imports `.adapter`, `.service`, `.model`, `.port`
  types. Never imports a driver.
- `cli.driver.ts`: triggers. Parse argv, pick the command, call `assemble()`
  once, call one use case, render, write. Imports `.assembly` and `.model`
  (parse/present). Loses the right to import `.adapter` or `.service` — that
  lost right is the door.
- `bin.ts`: the tech's entry, one import of the driver, as `+page` is the
  framework's.

**Why it is stronger than the merged driver:** the two verb lists are disjoint,
so each file kind rejects the other's material by construction. A `.command()`
chain or a switch over argv is neither init nor wire: red in `.assembly`. An
adapter factory call is none of resolve/call/parse/present: red in `.driver`.
Today's `main.ts` is red under both. With one file holding both lists, a
detector table sitting between an init and a trigger had nowhere to be caught.
The split closes that at the file level, before any verb reader runs.

**When assembly runs stays the driver's call.** The fs kernel needs the config
path from argv, so `assemble()` is called after parse, at the top or inside a
handler; "a prelude may live inside a handler" survives. Driver decides when,
assembly decides what.

**One arrow, both worlds.** CLI:
`bin → .driver → .assembly → services, adapters`. Web:
`+page.svelte → page.assembly.ts → services`, and `.svelte → .context` for
pulls. `.assembly` never imports a driver or a component (the arrow rixo ruled).
The web has `.context` because exposure is a registry; the CLI has none because
exposure is a return value. Same layer, two exposure mechanisms, the tech
adapter knows which.

**Literature:** this is Martin's Main and Seemann's composition root, two names,
which last night's capture had bent away from. Still ours: they have the root
call the adapters, we have the trigger file call the root, because the web
framework starts the component and we want one arrow in both worlds.

**Nested sidekicks (`FooSection` with `foo-section.assembly.ts`):** allowed and
visible — a runtime edge `.assembly → .service` per creator, so "same service
created from two assemblies" is a countable finding (the cache-created-twice sin
made observable). Seemann warns against multiple roots but scoped roots are his
own exception. Rule on evidence, not now.

**Roles on the web, one suffix, observable:** a `.svelte` importing `.assembly`
is a root caller; importing `.context`, a trigger; importing neither, a view.
Components are drivers; the tech suffix is the driver suffix. `.driver` (or the
config declaration) is for CLIs, plain TypeScript.

**What this reverses in tonight's earlier sections:** `page.driver.ts` becomes
`page.assembly.ts`; "`.driver` has the init right" becomes "`.assembly` has the
init right, `.driver`/`.svelte` have the trigger right"; the `assembly` config
key may survive with a changed meaning (suffix, not glob), which bears on the
slug-rename question.

**"So `.assembly` is the DI container?" (rixo) — No.** It is the composition
root, hand-written: Seemann's Pure DI, a factory chain in plain code. A
container resolves by token at runtime, reads metadata off services, auto-wires,
manages lifetimes; `.assembly` does none of that, the graph is imports and
calls, so `tsc` types it, the bundler splits it, the map reads it; swapping an
adapter is editing a line, there is no API for it. What it shares with a
container: it is the one place that knows the concrete graph, and services never
know it exists. The container-like piece is `.context`, half of one: a key →
instance map written by `.assembly`, read by triggers, no resolution, no
auto-init. That read is service location (Seemann's anti-pattern); his objection
is hidden dependencies inside the domain, and at the trigger ring it is what a
handler does anyway, with the `.context` import putting it on the map. **Locator
at the edge, pure DI inside** — say it in those words. What the checker gains
that a container hides: two verbs in `.assembly` (a definition that is neither
factory call nor wiring is red), and one runtime edge per creation, so a service
created twice is countable.

### Day three, continued — use cases are read on the service side; the fat store mediates the triggers (rixo's take-away)

rixo: triggers cannot be parsed reliably on every tech. A CLI's, yes. A web
app's (button events and the like), much more complex. Through the fat store the
triggers are mediated:

```ts
const service = createService({ ...deps })
const store = service.use_case()
// store.do_something() is a sub use case, store.do_something({ option }) a
// variant of it, store.do_something_else() another one
```

Take-away: **use cases are much more reliably detected on the service side.**
The complexity there is discriminating the primary (use) from the secondary
(instrumental) use case. And the store shows one more level up: a thematic
collection of use cases for a page or a standalone widget.

**Fable's read (inferred from what the extraction already sees):**

- The catalog comes from the service's export surface: a factory, the object it
  returns, its methods, and the methods on what those return. TypeScript,
  readable on every tech. The trigger side is a cross-check where the tech
  allows it: on the CLI both readings exist and reconcile (every use case called
  from some trigger, every trigger calling one); on the web only the service
  side exists, and that is enough.
- The fat store is the trigger-side door for the web. Handlers can only call
  what the store exposes, and every store method is code in a `.service` file
  under the full check. The container makes the one visible call
  (`.driver → .service`); below it is the store's business, unchecked at the
  call site because checked at the definition. Stronger than a Svelte reader
  would be: it lures the logic to the checked side instead of hunting it where
  it hides. What still escapes: a handler that computes before calling the
  store. Named, not zero.
- Primary vs instrumental is **altitude**, the user's intent, and only the
  author knows it. The checker sees **depth**: a method on the factory's object
  vs a method on a returned object. Depth is structural and drawable; altitude
  is a label. Cockburn's ladder gives words that do not collide with hexagonal
  primary/secondary adapters: summary level (the thematic bundle), user-goal
  level (what a user comes to do), subfunction (the steps in its service). The
  store fits either as a goal in progress with subfunction methods or as a
  bundle with goal methods; which one depends on the widget, not the code. The
  map draws the tree and stays silent on altitude. Suggested house words: use
  case / sub use case; avoid "secondary use case".
- Rule strength restated: "one trigger, one use case" becomes "one container,
  one factory-level call" on the web and "one command, one call" on the CLI.
  Below the factory level the store's methods are unbounded and uncounted. "Same
  service twice" survives: a container making two factory-level calls is
  probably two containers.

Standing: the service-side reading is inferred; the fat store is rixo's
hypothesis and the viewer builds its first one (the snapshot source), which is
the test.

### Day three, continued (2026-09-14 evening → 09-15) — the split, taken: assembly composes, driver fires

rixo's review of the morning's canon amendment, from a fresh session. It started
as three questions about the amendment and ended with the amendment replaced.
Standing marked as before: **ruled** (rixo said it as a decision), **inferred**,
**hypothesis**. The canon diff on the working tree is the result; this section
is why.

**The three questions, and what they found (verified against the diff).** Is the
full replacement of assembly by driver consistent with the activity vs role
framing? No: the paragraph called assembly a role, an activity and a right
within four sentences; "role" was the word the web research reserved for
observable postures, so canon saying "trigger role" pre-decided the `.svelte`
question. Is it consistent with the literature? Half: Seemann and Martin agree
assembly is not a layer (a location, a component outside the rings), and all
three keep root and primary adapter apart — the amendment merged them and placed
the merge under the section whose preamble says "the principles are Cockburn's".
Two Fable overclaims retracted on the spot: "'assembly is a point' was the
literature's form" (nobody says assembly or point; Seemann says "composition
root, a unique location", that is all) and "nobody calls a driver, the runtime
does" (the cac `parse()` call, an Express app dispatching, a custom server
inside the program all start drivers from program code).

**rixo's reframing (ruled in direction, then in shape):** program bootstrap vs
internal program inits. Something HAS to set up the driver; we rule the driver
and are undecided about how it is started; that undecided part is what we kept
calling "tech dependent". The amendment described tech-dependence from the
instrument's angle only (recognize, cut, attribute, exempt) and lost the
capture's first verb, "resolve the driver tech", so under a literal reading the
four rules forbade `cli.parse()` and `app.listen()` — the diff was
self-contradictory.

**The attempt to define the joint negatively, and why it failed.** "In a 100%
deblob codebase, the only thing unruled code may do is fire a driver." Fable:
true by construction (deblob rules what declared; the driver is the outermost
declaration; what starts it is beyond the last declaration) and therefore nearly
empty — and false as a fact about programs. If the starter is program code it
has two statuses and both bite: part of the driver layer (then the hand-off
precedent becomes a principle), or outside the surface (then it is an unruled
file importing drivers and tech, free to hold an auth middleware: assembly
reborn, the laundering venue the rules were cut to close, and blob under current
canon). rixo's answer was the split.

**The split (ruled).** A thin layer with one right — build and call a driver —
first named boot, then, once the tech moved into it, recognized as Cockburn's
driving adapter and renamed: **driver = the tech file that holds the hooks;
assembly = the composer.** What the morning's "strong version" did:

- The four driver rules were not added to, they were partitioned along the
  init/call line. `prelude-wiring-only` stayed on the composer; handlers-only,
  one-call, calls-services-only moved to the file that holds the tech. The
  composer becomes plain TypeScript with only factory calls, checkable
  identically for every tech; the per-tech rules sit where the tech is.
- The driver's rules then hold **without the "own tech" exemption**: the driver
  calls services and its tech; the composer calls factories and nothing else.
  The contradiction dissolves.
- One composer, several drivers: the same CLI assembly is called by the bin
  driver through cac, by a spec file, later by an HTTP driver.
- Deps of the composer: forbidden by essence as _injected services_ (nothing
  outside it may build a composition unit); allowed as _parameters from above_ —
  tech values from the driver, instances from a parent assembly. Fractal
  assembly at the top, same shape canon has for adapters.
- The composer is **not a composition unit and not an adapter** (rixo): it takes
  no injected deps, nobody composes it, it translates nothing. Calling it an
  adapter had bought exactly the tech permission and the "its port is the app's
  API" line, both of which belong to the hooks.
- `runtime-import`'s type exemption never reached it (rixo): the exemption is
  written for composition rules and its rationale is "a contract's shape", and
  the composer has no contract. No carve-out needed; one sentence saying so.
- **Nobody types a driver, nobody types an assembly** (rixo's tightening):
  consumers type against service API types. Consequence: the trigger role
  becomes visible by imports (a view typing its prop against `CheckServiceAPI`
  names the service it hooks into), the aggregate never travels (boot sets each
  service into context on its own key), and the wall is structural, not
  conventional.
- The thinnest legal composer returns an actual service, or a record of services
  (rixo: "that's always been our point — force all logic somewhere we can audit
  it"). Then the composer has no hooks, no triggers, no calls of its own;
  "trigger" leaves its vocabulary entirely. The wrapper caveat (two calls behind
  a structurally identical signature) dies with it: a function defined in the
  composer's return is a definition, and the composer defines nothing.

**Names (ruled).** "Root" is the literature's word for the composer, not for the
tech file, so the faithful mapping is composer = assembly (Martin's Main,
Seemann's composition root), tech file = driver (Cockburn's driving side). It
partially reverses the morning: assembly is a place again — but what the morning
killed and what stays dead is the _blend_ (assembly as everything outside the
hexagon); what returns is the activity with a file and one right. rixo's
day-three objections answered: per driver, not central; assemblies may call
assemblies' factories (fractal, closes the service-sharing seam); what it brings
is no tech, invisible to the UI, checkable for every tech, one file to read for
wiring. Tone: tune down the assembly bashing if it is ruled fully. `assembleCli`
over `createCliAssembly` — implementation guide. "Some sort of DI container?" —
in role yes, in mechanism deliberately not (Pure DI, static, readable); at
theory level deblob has no opinion on containers: a runtime container still
imports what it weaves, so it is an assembly by imports, entering only through
an explicit config whitelist next to `pure`.

**"Prelude" (ruled): by verb, not by position.** Wiring is a verb set (assembly
calls, tech setup, sub-driver registration); hook is a position (the callback
the tech fires); wiring may sit inside a hook (lazy). The rule reads: outside
hooks, wiring only; inside a hook, wiring plus one call. "Prelude" survives at
most as a slug word, not as a concept.

**Shapes walked through (inferred, rixo-confirmed):**

- deblob's CLI today: `bin.ts` is already the driver's process glue nearly

  Target: `cli.driver.ts` (process, cac, one hook per command),
